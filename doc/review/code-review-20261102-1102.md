## Summary

The branch fixes the debug argument pre-parser so its grammar matches the one
Spectre.Console.Cli actually applies (0.57.x):

- A bare `--debug` flag now enables debug regardless of position (previously a bare flag in
  last position returned `false`).
- `--debug true` / `--debug false` (separated tokens) are honored as explicit values, matching
  Spectre's `CliConstants.AcceptedBooleanValues` handling for flag parameters.
- A new `--debug=value` inline form is recognized; only `true` enables debug, and any other
  inline value fails closed because Spectre rejects such values with
  `CannotAssignValueToFlag`.
- `--logfile=value` inline form is newly recognized.
- `[DefaultValue("false")]` on `InitAdrSettings.Overwrite` is corrected to
  `[DefaultValue(false)]` (type-safe object, no string coercion).
- CLI examples in `CommandConfiguration` are updated to the corrected grammar.

I verified the grammar assumptions against the Spectre.Console.Cli source
(`CommandTreeParser.ParseOptionValue`): for a `ParameterKind.Flag`, a following string token in
`AcceptedBooleanValues` (`"true"`/`"false"`, `OrdinalIgnoreCase`) is consumed as the flag's
value; a non-boolean token without a `=` separator is intentionally *not* consumed (treated on
the next pass as a positional argument or parse error); an inline value with `=` other than
`true`/`false` is rejected outright. The new `ArgumentHandler` semantics are a faithful
mirror of that behavior, including the deliberately "permissive" bare-flag fallthrough which
is the safe outcome (logging gets configured for a run that is about to fail at parse time).
This is well-documented in the new XML doc comments.

Overall this is a clean, well-motivated fix with substantially improved test coverage. Findings
below are minor.

## Findings

### 1. [Low] `LogFile`: bare flag followed by an option token yields the option token as the "filename" — ✅ Resolved

> **Resolution.** The separated form now mirrors Spectre's tokenizer: a token that starts with `-` is not treated as
> the option value, except tokens where the character after the dash is a digit (for example `-1` or `-1.log`), which
> Spectre keeps as strings. `LogFile` returns `string.Empty` for `--logfile --debug`, `--logfile -o`, `--logfile --`
> and `--logfile -`, and still returns `-1.log` for `--logfile -1.log`. Covered by
> `LogFile_Argument_Followed_By_Option_Returns_Empty_String`, `..._Short_Option...`,
> `..._End_Of_Options...` and `..._Negative_Number_Value...`.

`src/DotAdr/ArgumentHandler.cs`, `LogFile`:

```csharp
if (args[i].Equals(LogFileOption, StringComparison.OrdinalIgnoreCase))
{
    // Check if this is the last argument
    if (i == args.Length - 1)
    {
        return string.Empty;
    }

    return args[i + 1];
}
```

For `dotadr init --logfile --debug`, the token `--debug` tokenizes as a *LongOption* in Spectre,
so `valueToken?.TokenKind == CommandTreeToken.Kind.String` is false and Spectre ultimately
fails the run with "The option 'logfile' has no value". The pre-parser instead returns
`"--debug"` as the log file path, and Serilog will create a file literally named `--debug`
during a run that fails at parse time. This pre-dates the branch, but since this file's stated
goal is now "aligned with the Spectre grammar" and the empty-inline-value case was explicitly
made fail-safe, the equivalent case for the separated form is worth closing in the same
spirit:

```csharp
// A token starting with '-' tokenizes as an option in Spectre, not as a value:
// "--logfile --debug" ends in OptionHasNoValue, so treat it as no value.
return args[i + 1].StartsWith('-') ? string.Empty : args[i + 1];
```

(Add a test like `LogFile_Argument_Followed_By_Option_Returns_Empty_String` alongside it.)

### 2. [Low] Missing Spectre-acceptance coverage for the separated `--debug true/false` forms — ✅ Resolved

> **Resolution.** `With_Debug_And_LogFile_Syntax_Accepted_By_Spectre_Returns_0` now includes `--debug true` and
> `--debug false`, so the separated flag-value forms that `IsDebugMode` consumes are locked by the real Spectre parser
> as well as by the helper tests.

The new `RunAsync` theory in `test/DotAdr.Tests/Commands/InitAdrCommandTests.cs` locks the
parse-acceptance contract for the inline forms, but not for the separated forms that
`IsDebugMode` now consumes:

```csharp
[InlineData("--debug")]
[InlineData("--debug=true")]
[InlineData("--debug=false")]
[InlineData("--logfile=app.log")]
[InlineData("--debug", "--logfile", "app.log")]
```

`RunAsync.With_Overwrite_Syntax...` proves Spectre accepts `-o true` / `-o false` for a flag
parameter, but adding `--debug`/`true` and `--debug`/`false` cases to the first theory would
directly encode the exact grammar assumptions that `IsDebugMode` relies on (and that the new
XML doc comments claim), keeping the helper and the real parser in sync if Spectre changes:

```csharp
[InlineData("--debug", "true")]
[InlineData("--debug", "false")]
```

### 3. [Low] Extract the value literals alongside the option-name constants — ✅ Resolved

> **Resolution.** `TrueValue` and `FalseValue` constants were added, plus a private `IsTrue` helper that both the
> separated and inline branches use. The grammar tokens now live alongside the option-name constants and are easy to
> compare with `CliConstants.AcceptedBooleanValues` on a future Spectre version bump.

`src/DotAdr/ArgumentHandler.cs` now repeats the string literals `"true"` / `"false"` four
times, mixed with the OrdinalIgnoreCase comparisons. With `DebugOption` and
`DebugOptionPrefix` already extracted, the value constants complete the pattern:

```csharp
private const string TrueValue = "true";
private const string FalseValue = "false";
```

Small, but it keeps the entire grammar the pre-parser mirrors in one place and makes it
trivially comparable to `CliConstants.AcceptedBooleanValues` when re-reading the align-back
against Spectre in a future version bump.

### 4. [Low] Duplicate first-occurrence-noted-but-last-wins divergence in Spectre

Both helpers return on the *first* matching `--debug` / `--logfile` token. If Spectre ever binds
a repeated option with last-wins semantics (typical option-binding behavior), the two parsers
would disagree for inputs such as `--debug false --debug true`. This is a theoretical edge
("why would anyone do that?") and consistent with the existing `Multiple_LogFile_Arguments`
first-wins test, so it needs no code change now, but it belongs on the known-divergences list
in the `AdrSettings.Documentation` / XML remarks if you keep that list. Noting it for the
record since the branch's stated goal is exact grammar parity.

### 5. [Low] Test duplication in the new `RunAsync` suite

In `test/DotAdr.Tests/Commands/InitAdrCommandTests.cs`, every new test repeats:

```csharp
using var console = new TestConsole();
console.EmitAnsiSequences = false;
var configurationService = new Mock<IConfigurationService>();
var app = CreateApp(console, configurationService.Object);
```

The console is created outside the helper but only used inside it. Fold it in:

```csharp
private static CommandApp CreateApp(out Mock<IConfigurationService> configurationService)
{
    using var console = new TestConsole();
    console.EmitAnsiSequences = false;
    IAnsiConsole ansiConsole = console;
    configurationService = new Mock<IConfigurationService>();
    ...
}
```

Note the `using`/lifetime caveat: the registered `ansiConsole` instance must outlive
`await app.RunAsync(...)` inside the test body, so keep that in view when moving the
construction (the current explicit placement is actually the clearest expression of that
ordering, so this is a judgment call — the repetition alone doesn't warrant the abstraction
yet). At minimum, a shared local factory inside `RunAsync` would remove three lines per test.

### 6. [Info] The spectrum of "non-boolean after bare flag" differs from the inline form by design

`--debug yes` → debug enabled (token is handed to Spectre as a positional/parse error);
`--debug=yes` → debug disabled (Spectre rejects inline non-boolean values). This asymmetry is
correct — it is exactly what Spectre does — and the new `<remarks>` block explains it. No
action needed; flagging only because it surprised one of the rewritten tests
(`Debug_Flag_With_Non_Boolean_Token_Returns_True` vs `Debug_Flag_Equals_Unrecognized_Value_Returns_False`)
and deserves the explicit test-story it now has.

### 7. [Info] `IsDebugMode` doc-comment wording — ✅ Resolved

> **Resolution.** The summary now states that an inline value is enabled only when it is `true` and that every other
> inline value returns false, removing the apparent contradiction with the remark about bare flags.

The `<summary>` says the helper "fails closed (returns false)" for inline non-`true` values,
which reads as a contradiction of the adjacent remark where a bare flag plus arbitrary token
returns `true`. Both are true statements, but they answer different questions; consider
narrowing the sentence to "fails closed (`--debug=false`) for inline values that are not
explicitly `true`". Purely a wording refinement.

### 8. [Positive] `DefaultValue(false)` on `InitAdrSettings.Overwrite`

`[DefaultValue("false")]` was passing a `string` for a `bool` property — the corrected,
type-safe form removes reliance on string conversion in help/example rendering and matches
`AdrSettings.Debug` which already used `[DefaultValue(false)]`.

### 9. [Positive] Verification story for the grammar contract

The branch pairs pure helper tests (`ArgumentHandlerTests`, 22 new cases including case
variants, inline/separated forms, empty values) with end-to-end parse tests through the real
Spectre pipeline (`InitAdrCommandTests.RunAsync`, with an isolated DI registration and mocks
so no filesystem side effects occur). The comment explaining `config.Settings.Console` /
static console caching is exactly the kind of "why" a future maintainer needs.

## Verdict

No blocking issues. The core risk — divergence between the pre-parser and Spectre's flag
grammar — is now measurably reduced: I independently confirmed the alignment against the
Spectre.Console.Cli parser source (flag values accepted as `true`/`false`
`OrdinalIgnoreCase` separated tokens, inline values rejected unless in
`AcceptedBooleanValues`, non-boolean tokens after a bare flag left for the next parser pass).
Recommend the three low-severity follow-ups (findings 1, 2, 3), of which #1 is the only one
affecting production behavior (a stray log file created for a doomed run).
