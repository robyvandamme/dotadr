## Summary

The approach changed fundamentally since the first review: instead of fixing the `ArgumentHandler`
pre-parser's grammar, the pre-parser was deleted. `LoggingInterceptor` (`ICommandInterceptor`)
now configures Serilog from the *bound* `AdrSettings.Debug` / `LogFile` values right after Spectre
binds settings, and `DelegatingLogger` — registered as the DI `ILogger` — forwards every call to
the current `Log.Logger`, so commands still resolve a logger that reflects the post-interceptor
configuration. `LoggerConfigurator.Configure(bool, string?)` is now parameter-based, and
`Program.cs` shrinks to `new CommandApp().Configure(...)` + `RunAsync` + flush.

I verified the correctness claims against the Spectre.Console.Cli source (`CommandExecutor`):

- Settings binding happens first, then registered `ICommandInterceptor`s run
  (`foreach (var interceptor in interceptors) interceptor.Intercept(context, settings)`), *then*
  `command.Validate(context, settings)`. So settings-validation failures (e.g. missing template
  path) **are** covered by the interceptor's logging configuration. Good placement choice.
- However, parse failures (`CommandParseException`), `--help`, and `--version` short-circuit
  **before any interceptor runs** — see finding 1.

I also verified the `DelegatingLogger` viability against Serilog 4.4 source: `ILogger` in Serilog 4
implements all convenience overloads (including `Debug`/`Information`/`Error` and `ForContext`) as
default interface methods that funnel into the three members the class overrides
(`IsEnabled`, `Write(LogEvent)`, `Write(level, exception, template, params)`), and the `ForContext`
defaults wrap `this`, so context loggers created before the interceptor swap still route to the
reconfigured sink. The pattern is sound.

## Findings

### 1. [Medium] Parse-phase and help-path failures no longer get any logging — including for users who explicitly requested `--debug` / `--logfile` — ✅ Resolved (accepted trade-off)

> **Resolution.** Accepted as a documented limitation rather than mitigated with a bootstrap logger. A bootstrap
> logger in `Program` cannot honour `--logfile`, because the path is only known after parsing; it would only
> duplicate the console output that `AnsiConsole.WriteException` already provides. The README now states that parse
> errors are reported on the console but not written to `--logfile`, and
> `InitAdrCommandTests.RunAsync.With_Parse_Error_Does_Not_Create_Log_File` pins the behaviour (the run exits non-zero
> and creates no file). The regression relative to the old flow is limited to invalid invocations: Debug builds lost
> the file copy of the parse error, and Release builds with `--debug` lost the startup-lines file.

`src/DotAdr/Program.cs` no longer configures a logger before `RunAsync`, and Serilog's default
static logger is `Logger.None` (a `SilentLogger` that drops every event — verified in Serilog
source). Because Spectre runs interceptors only *after* settings binding, a run that fails during
parsing (unknown command, `dotadr init --logfile` with a missing value, an inline
`--debug=yes`-style value Spectre rejects, etc.) reaches the `catch` in `Program.cs` and logs via
the silent logger:

```csharp
catch (Exception ex)
{
    Log.Error(ex, "An error occurred");   // silently dropped unless the interceptor already ran
    AnsiConsole.WriteException(ex, ExceptionFormats.ShortenEverything);
    return 1;
}
```

Benefits of the old flow (both buggy and fixed versions of the pre-parser configured logging
up front): on those doomed runs, `--logfile` created a file you could inspect with the parse
error in it. Now the only diagnostics are the raw exception on stdout, and nothing in the log
file the user explicitly asked for. This is the real regression risk of the trade — and it also
applies to interceptor *internal* failures (e.g. `Serilog.Sinks.File` throwing on an invalid
path during `LoggerConfigurator.Configure`).

Suggested mitigation (pick one):

```csharp
// Option A: bootstrap logger in Program.cs, refined by the interceptor afterwards.
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Error()
#if DEBUG
    .WriteTo.Console()
#endif
    .CreateLogger();
```

- **Option A** (above): a default Error-level bootstrap logger before `RunAsync`; the interceptor
  replaces it from the bound settings. Cost: nothing for happy paths, and the catch block becomes
  useful again. Serilog's `CreateBootstrapLogger()` two-phase pattern (via
  `Serilog.Extensions.Hosting`) is the idiomatic variant but adds a package dependency.
- **Option B**: keep the silent default but special-case the `catch` — if no run reached the
  interceptor, write the exception to stderr directly (Spectre's `WriteException` already covers
  the human-readable part, so this is mostly about honoring an explicit `--logfile` request).
  Slightly more code for less benefit — A is simpler.

Either way this deserves a decision in review: it's the only behavioral gap introduced by
removing the pre-parse step, and it's invisible in the happy-path tests the branch adds.

### 2. [Low] The acceptance tests never exercise the component that consumes the bound settings — ✅ Resolved

> **Resolution.** Added `InitAdrCommandTests.RunAsync.With_LogFile_Configures_Logging_End_To_End`, which registers
> the real `LoggingInterceptor`, runs `init --debug --logfile <temp>/app.log` through `CommandApp.RunAsync`, flushes
> the logger, and asserts the rolling file contains `Starting init`. A dedicated test with a temp directory is used
> instead of registering the interceptor in the shared acceptance theory, so the theory keeps its no-file-side-effect
> behaviour.

`InitAdrCommandTests.RunAsync.CreateApp` registers mocks and `InitAdrCommand`, but no
`ICommandInterceptor`, so the `--debug` / `--logfile` InlineData cases validate parse acceptance
only — the new wiring (`LoggingInterceptor` consuming `AdrSettings.Debug`/`LogFile`) is not
covered end-to-end at the app level.

Consider registering the interceptor in the test app to mirror production wiring:

```csharp
config.Settings.Registrar.RegisterInstance<ICommandInterceptor, LoggingInterceptor>(
    new LoggingInterceptor(new VersionInfo(typeof(InitAdrCommand).Assembly)));
```

Caveat if you do: the `--logfile=app.log` InlineData would then actually create the file next to
the test working directory, so either keep it in a dedicated test with cleanup, or point the
inline value at a temp directory. Alternatively a single end-to-end test asserting that
`dotadr init --logfile=<temp>/app.log` produces a file containing `Starting init` would directly
close the loop between "Spectre accepts it" and "the logger is actually configured with it"
(the interceptor unit test covers the latter in isolation, but only through the
mocked/real `Log.Logger`, not through the app pipeline).

### 3. [Low] Untested: the `settings is not AdrSettings` no-op branch — ✅ Resolved (documented)

> **Resolution.** Documented on `AdrSettings` instead of adding a test for the guard: every command settings type
> must derive from `AdrSettings`, otherwise the interceptor leaves logging unconfigured. The early return remains as a
> defensive guard; a test for a path that production commands cannot reach was considered low value.

`LoggingInterceptor.Intercept` early-returns for settings that don't derive from `AdrSettings`.
This guard protects the logging configuration, but no test covers it. One small theory entry in
`LoggingInterceptorTests` would do:

```csharp
internal sealed class ForeignSettings : CommandSettings { }

[Fact]
public void With_Unknown_Settings_Leaves_Logger_Untouched()
{
    var originalLogger = Log.Logger;
    try
    {
        var interceptor = CreateInterceptor();
        interceptor.Intercept(CreateContext("init"), new ForeignSettings());
        Log.IsEnabled(LogEventLevel.Debug).ShouldBeFalse();
    }
    finally { ResetLogger(originalLogger); }
}
```

Also worth a sentence in the `AdrSettings` doc comment: any *future* command settings type must
derive from `AdrSettings` or it silently gets no logging configuration.

### 4. [Info] `DelegatingLogger` has a hidden version dependency worth a one-line comment — ✅ Resolved

> **Resolution.** Added a `<remarks>` note explaining that only `Write(LogEvent)` and `IsEnabled` are forwarded and
> that the remaining `ILogger` members are Serilog 4 default interface implementations funnelling into
> `Write(LogEvent)`; the small surface is intentional. The explicit `Write(level, exception, template, values)`
> override was later removed because CA2254 flags a non-constant template passed to a logging method, even in a pure
> forwarder; the default implementation performs the binding and calls `Write(LogEvent)`.

The class overrides only `IsEnabled`, `Write(LogEvent)` and the
`Write(level, exception, template, params)` overload. This works because Serilog 4.0+ implements
the rest of `ILogger` (including `ForContext` and all typed overloads) as default interface
methods that funnel into those three. If the project were ever pinned to Serilog 3.x, the class
would not compile — which is fine as a safety property — but a maintainer reading the file has no
hint that the small surface is intentional. Consider extending the existing summary:

```csharp
/// ... The other ILogger members are provided by Serilog 4's default interface implementations,
/// which funnel into the forwarded members above.
```

### 5. [Info] Configuration-time exceptions land outside the `try` in `Program.cs` — ✅ Resolved

> **Resolution.** `VersionInfo` construction, `new CommandApp()` and `Configure(...)` now run inside the `try`, so
> configuration failures are logged (when a logger is configured), rendered by `AnsiConsole.WriteException`, and the
> `finally` flush still runs. No dedicated test: forcing `Configure` to throw would need a test-only seam, and this is
> a straightforward control-flow move.

`commandApp.Configure(new DelegatingLogger(), versionInfo)` runs before the `try` block, so any
exception during app configuration (including `ValidateExamples()` in DEBUG builds) bypasses the
catch/flush and produces an unhandled crash without the AnsiConsole output. This is pre-existing
(the previous version had the same shape), unchanged by this branch, and unlikely to bite in
production — noting it so it doesn't get lost: if the exception path ever matters, move the
`Configure` call inside the `try` and keep the `finally` flush.

### 6. [Positive] Net simplification with a genuinely better separation of concerns

- 66 lines of bespoke grammar-mirroring logic (and 158 lines of tests maintaining it) replaced by
  the library's own parse result; the two parsers can no longer drift, which was the core risk
  the first review found.
- `DelegatingLogger` solves the real ordering problem (DI logger registered before logging is
  configured) with the minimal forwarding implementation and a doc comment that explains *why*.
- `LoggerConfigurator` now takes parsed values, is trivially testable, and has no argument-shape
  knowledge left.
- Grammar coverage is preserved through real `RunAsync` Spectre-pipeline tests rather than
  home-grown string matching.

### 7. [Positive — carried over] `DefaultValue(false)` on `InitAdrSettings.Overwrite`

The type-safe `[DefaultValue(false)]` fix survives the refactor; examples in
`CommandConfiguration` were updated consistently (`-o` bare flag, `--debug --logfile log.txt`),
and the DEBUG `ValidateExamples()` will keep them honest.

## Verdict

The refactor is a clear improvement over the pre-parser approach and I could not find a
correctness bug in the new wiring — the interceptor placement matches Spectre's execution order,
and the `DelegatingLogger` forwarding is sound against Serilog 4.4. The one substantive gap is
finding 1 (parse-phase/help-path failures silently lose logging, regressing parity with the old
`LoggerConfigurator.Configure(args)` invocation), which merits either a bootstrap logger in
`Program.cs` or an explicit decision to accept the trade — it is user-visible only in failure
paths and only when the user explicitly asked for logging.
